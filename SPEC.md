# Standalone OpenCode V2 generate_image plugin

## Objective

Add a native `generate_image` tool to OpenCode V2 using its already-authenticated OpenAI ChatGPT subscription and automatic native OAuth refresh. There is no separate CLI login, credential copy, or API-key billing fallback.

## Scope and architecture

- Target installed OpenCode V2 2.0.25 and `@opencode/plugin` 2.0.25, not the unrelated V1 `opencode` binary.
- Standalone package in this repository. It is independent of external CLIs and prior image implementations at runtime.
- Native tool named exactly `generate_image`, discoverable through Code Mode with permission `generate_image`.
- Resolve the active `openai` connection through `ctx.integration.connection.active` and `resolve` for every invocation. OpenCode owns refresh invocation at `expires <= now + 5 minutes` and rotated-token persistence through `credentials.update`. There is no platform-wide singleflight guarantee; the provider semaphore only serializes switched-triggered registry loads. Do not implement a plugin refresh, cache credentials, overwrite native OAuth methods, or access auth files or databases. Stop waiting on cancellation without duplicating platform-owned refresh.
- Serialize the entire active/resolve/validation sequence in a module-shared FIFO, retaining the gate until native settlement even when a caller stops waiting. Each queued invocation re-reads active state. This protects image calls sharing this module, not ordinary model calls or other processes.
- Pass cancellation into image normalization and stop waiting on every native Sharp await; do not claim termination of native codec work. Preserve byte/pixel limits and prevent subsequent requests or writes after cancellation.
- Provide a root `index.ts` for local package-folder loading and verify that entry through the isolated native config loader without contacting the subscription endpoint.
- Use the fixed HTTPS subscription endpoint `https://chatgpt.com/backend-api/codex/responses`. There are no production endpoint overrides, bearer redirects, auth logs, or arbitrary downloads.
- Support Sunburst/Flare, validated quality and size, up to five project-relative references, generate/edit, and PNG output with actual dimensions. Alpha is preserved when the provider returns it, but there is no `transparent` request option and no chroma-key/green-screen processing; that scope is deliberately omitted.
- Use Linux `/proc/self/fd` descriptor-relative access and Windows x64 NT handle-relative access on local NTFS volumes; other platforms fail closed. Use project-root-contained paths with no hidden or traversal segments, symlink ancestors, hardlinked references, or non-regular files. Never overwrite an existing output. Respect cancellation and timeouts, use bounded response/reference decoding, and return sanitized errors. Do not automatically retry quota-consuming POSTs.
- Only the explicit prompt and references are sent, not session history.
- Outer-model option: `imageOptionsSchema.responsesModel` is optional and validated, with no schema default. For each invocation after `ctx.session.get`, select the explicit override, otherwise the current `openai` session model ID, otherwise `DEFAULT_RESPONSES_MODEL = "gpt-6.1-sol"`. Reject identifiers without a lowercase `gpt-` prefix or containing provider prefixes, `#` variants, whitespace or unsafe characters, or exceeding 200 characters. Explain invalid native aliases and variants and require an explicit actual API ID rather than silently falling back.
- Preserve injected test backends. Default production backend and service creation happens per invocation; `CodexImageBackend` accepts an optional third outer-model argument, and `imageRequest` accepts an optional third outer-model argument. Both validate and default to `DEFAULT_RESPONSES_MODEL`. The second constructor endpoint seam remains fixed production or loopback only; outer model selection never affects the URL, credentials, image tool model, or automatic retry policy.

## Acceptance checks

1. Exact tool registration and public types compile against 2.0.25.
2. Hermetic protocol tests verify request payload, account header, complete SSE image extraction, refusals, malformed and oversized streams, cancellation, and no automatic retry.
3. Filesystem tests verify reference validation, PNG output, no overwrite, and contained paths.
4. A real isolated OpenCode 2.0.25 host test executes through Code Mode with synthetic OAuth: the expired access token is refreshed natively, the rotated credential is used, permissions prevent generation, and credentials never enter history.
5. Independent review of security boundaries, authentication, and failure behavior; findings are resolved or explicitly documented.
6. Add one plugin entry to the OpenCode V2 config, preserving unrelated config with a reversible backup; verify the plugin and tool on the running service if a reload can be done without stopping current sessions.
7. Attempt one small live image as acceptance using the existing OAuth connection if the tool becomes available without a disruptive restart. Clearly distinguish actual subscription verification from hermetic verification if blocked.
8. Model-selection regression checks assert actual request bodies for default and explicit outer models and the production-default registration path in an isolated native host (fixed URL intercepted into loopback): current OpenAI session model per invocation, plugin override precedence, and non-OpenAI default. Strict option and identifier tests protect rejected aliases and variants and explain the override before OAuth or POST. No live POSTs are needed for these checks.

## Non-goals

No edits to external Codex or CLI sources, provider methods, authentication storage, or unrelated OpenCode configuration. No deployment, commits or pushes, recursive deletion, or disruptive service restart as part of plugin implementation.

## Provider response handling and diagnostics

- Keep the request payload, fixed endpoint, and `redirect: "error"` unchanged. HTTP 401 and 429 retain reconnect and quota messages; other non-2xx bodies may be inspected but never logged or returned.
- Inspect at most 16 KiB of valid UTF-8 JSON under the caller's cancellation or timeout; cancel and release the reader without waiting for peer acknowledgement. Unknown, malformed, unreadable, or oversized bodies retain the generic HTTP-status message. No automatic retry.
- Only `error.{code,type,param,message}` or `detail` (a string or the same record fields) are inspected. Recognized rejection vocabulary includes `unsupported_tool`, `unsupported_model`, `model_not_found`, `subscription_required`, `invalid_parameter`, `invalid_value`, `unsupported_parameter`, `unsupported_value`, and `invalid_request_error` with exact whitelisted request field names. Anchored reason phrases map recognized messages to owned static text; this vocabulary is a compatibility classifier, not evidence that any particular error occurred live. No recursive search, captured text, URLs, prompts, values, or credentials enter diagnostics.
- Success responses may be incremental `text/event-stream` or a strict whole completed `application/json` Responses object (`object: "response"`, nonempty string `id`, completed status and output). Normalize media-type case and surrounding whitespace. Under `application/json`, `text/plain`, or an unknown or missing label, sniff the explicit SSE prefix (`data:`, `event:`, or comment `:` after optional empty lines) within 1 KiB and use the SSE validator when present. The `application/json` and unknown or missing paths may otherwise parse the strict whole JSON object; JSON under `text/plain` remains rejected. Explicitly reject known `text/html`, `application/octet-stream`, and raw `image/*` labels. Read whole JSON in bounded 64 KiB blocks. Rejected-type diagnostics use owned static text and include only exact known media-type names.
- Require `response.completed`, status `completed`, and an array `output` (empty is allowed). Validate and refusal-scan final items; every final image entry needs completed status and a nonempty bounded full result, and multiple final image entries are rejected even if identical. Combine done and final results through the existing ID-keyed deduplication/conflict map and require exactly one unique completed image before selecting it. A streamed done image may be retained when final output is empty, but only after successful whole completion. JSON without streamed results still requires one full final image.
- Reject partial, pending, incomplete, failed, refused, truncated, malformed, oversized, multiple-image, and noncanonical-base64 results. Reject any non-null completed `response.error` or `response.incomplete_details` before selecting or releasing an image. Release bytes only at stream `finish()` after framing checks; service validation still requires a complete single bounded PNG before exclusive contained output.
- Preserve the 96 MiB wire and 32 MiB image bounds, 20,000-event and 100,000-line limits, 16-megapixel decoded limit, fatal UTF-8 decoding, cancellation and reader release, fixed authenticated endpoint, outgoing headers and body, account header, no redirects, and no POST retry. HTTP 200 JSON error envelopes never supply an image.
- Cardinality failures report a fixed-key JSON summary: `final_output`, `final_image_generation_call`, validated `streamed_image_items`, unique `streamed_image_results`, and `done` and `final` type counts. Counters saturate at 20,000. Diagnostics are bounded and no persistent logs are written. Unknown names, text, prompts, arguments, base64, IDs, model names, credentials, and arbitrary headers never enter diagnostics.
- Test caveat: protocol JSON fixtures are examples, not evidence of a captured subscription JSON response. Bun's loopback can re-add `text/plain` for string bodies, so genuinely missing-label host cases delete the header and use the real response or stream through the fetch-boundary stub.
- Earlier live failures and intermediate fixes are historical diagnostic evidence. They are superseded by the live-verified acceptance below and are not current status.

## Accepted filesystem threat boundary

Descriptor-relative, no-follow I/O pins authorized directory inodes; containment assumes stable directory topology during the operation. On Linux, a same-user process capable of renaming an already-open authorized directory outside the project can relocate that inode after a containment check. Windows x64 uses NT handle-relative access on local NTFS and rejects UNC and network volumes; reparse-point checks are not atomic with subsequent opens or I/O, and a timed mutation and restoration can evade them. This plugin is not a same-user filesystem sandbox and does not attempt to prevent arbitrary concurrent topology mutation.

## Deployment and live-verified acceptance (2026-10-14)

- The standalone plugin is installed in OpenCode V2 global config as an object entry for a local package folder. Existing settings and the primary model entry are unchanged, and a reversible backup was taken before the change. The wrapper `options.responsesModel` is outer-Responses configuration only; the image `model` argument remains `gpt-image-2.5-sunburst` (default) or `gpt-image-2.5-flare`.
- Root `index.ts` exposes the default plugin. `generate_image` is registered Code Mode only. `/api/plugin` showed `generate-image` active from `index.ts`.
- Per-call native auth (`active` plus `resolve`, refresh at `expires <= now + 5 minutes` with persistence) needs no extra login, API key, or copied tokens. Live calls used the current authenticated OAuth connection without forcing real expiration; refresh, rotation, and persistence are covered by synthetic expired credentials in the isolated host.
- Live acceptance is **verified**: 10 native generation POSTs. The first 7 failed with diagnosed issues (three HTTP 400, with the third classified as unsupported outer `gpt-5.5`; media-format gates; and cardinality). The seventh supplied the root-cause safe counts (`final_output: 0`, `streamed_image_results: 1`): the image arrived in `response.output_item.done` while `response.completed.output` was empty. The retained-stream fix releases that result only after successful whole completion with refusal, exactly-one-image, canonical-base64, bounds, PNG, and the shared completed-error guard.
- The final three calls saved a Flare `low` generation, a Sunburst `low` reference edit, and a default Sunburst `auto` generation. Each PNG is `1254x1254` with mode `0600` under `generated-images/`; all three were visually verified and independently PNG/Sharp checked. Two native preflight rejections (existing output and traversal) never POSTed and are not counted in the 10.
- Cancellation is proven by a real host `session.interrupt` (`resume: false`) with server-observed `request.signal` abort: one POST, no retry, no file, and no history leak.
- Fresh `bun run check` passed typecheck, 352 unit tests (1,362 assertions), and 5 isolated host tests (40 assertions), zero failures. An independent review confirmed that non-null completed `error` and `incomplete_details` now reject (4 counterexamples; focused 270 tests and 1,180 assertions; no new blocking defect).
- Detailed machine-local logs, hashes, and artifact paths were produced during acceptance but are intentionally not part of this repository.
